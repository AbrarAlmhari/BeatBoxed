# Data Model (proposed — lock in Week 1)

This is a starting proposal for the Supabase/Postgres schema, sized to the MVP feature list. Treat it as a draft to be finalized by the team in the first work session, then locked — changes after parallel build starts should be flagged to everyone, not migrated silently.

## Core tables

- **profiles** — `id (uuid, fk auth.users)`, `username`, `display_name`, `avatar_url`, `bio`, `theme_preference`, `translation_language`, `favorite_genres`, `friends_list_visible (default true)`, `is_private (default false)`, `created_at`. `username` is unique case-insensitively. `friends_list_visible` (name kept from the friends era) gates both `get_followers()` and `get_following()`, and is the Settings switch "Show my followers and following". `is_private` limits reviews, playlists, followed artists and both follow lists to accepted followers, through `can_view_profile()`; switching it from true to false accepts every pending follow request (trigger `accept_requests_on_public`).
- **artists** — `id`, `spotify_id`, `name`, `image_url`, `genres` (cached from Spotify Client Credentials lookups, not a full mirror)
- **albums** — `id`, `spotify_id`, `title`, `artist_id (fk)`, `cover_url`, `release_date`
- **songs** — `id`, `spotify_id`, `title`, `artist_id (fk)`, `album_id (fk)`, `duration_ms`, `genre`, `popularity` (nullable; Deezer rank, see note below)
- **reviews** — `id`, `song_id (fk)`, `user_id (fk)`, `rating (1-5)`, `title`, `body`, `created_at`, `updated_at`, `edited (bool)` — unique on `(song_id, user_id)`: one review per user per song, so writes are edit-or-create
- **review_reports** — `id`, `reporter_id (fk profiles, cascade)`, `review_id (fk reviews, cascade)`, `reason`, `created_at` — unique on `(reporter_id, review_id)`. Filled from the feed's "…" → Report. Insert only as yourself, only for a review you can see and that isn't yours; you can read only your own reports; no update or delete. No moderation screen: the team reads it in the dashboard.
- **review_likes** — `review_id (fk, cascade)`, `user_id (fk, cascade)`, `created_at` — primary key `(review_id, user_id)`, so a like is binary and can't be duplicated
- **review_comments** — `id`, `review_id (fk, cascade)`, `user_id (fk, cascade)`, `body (not null)`, `created_at`, `updated_at`, `edited (bool)`
- **song_views** — `user_id (fk, cascade)`, `song_id (fk, cascade)`, `viewed_at` — primary key `(user_id, song_id)`, so a revisit updates the timestamp rather than adding a row. Seeds Explore's For You song rail, and feeds Explore's Recently viewed rail together with `play_history`.
- **play_history** — `user_id (fk, cascade)`, `song_id (fk, cascade)`, `played_at`, `position_seconds` — primary key `(user_id, song_id)`, so replaying a song moves its timestamp rather than adding a row. Feeds Explore's Recently viewed rail together with `song_views` (newest first, each song once). `position_seconds` is **no longer written or read**: resume-from-position was removed and every play starts from the beginning; the column stays, unused, to avoid a schema change. **Private**, scoped to the owner on every policy, like `song_views`. Kept deliberately separate from `song_views`: opening a song's page is not the same signal as listening to it. A row is only written once playback has actually run for 5 seconds, so tapping play and skipping on leaves no trace;
- **playlists** — `id`, `user_id (fk)`, `title`, `description`, `cover_url`, `created_at`, `updated_at`. `updated_at` is maintained by triggers, not the client, and moves both when the title/description change and when a song is added, removed or reordered. `cover_url` is unused: covers are derived at render time from the first four songs' album art (2×2 grid, a single image for 1–3 songs, the gradient placeholder when empty) — there is no custom cover upload.
- **playlist_songs** — `playlist_id (fk, cascade)`, `song_id (fk, cascade)`, `position`, `added_at` — primary key `(playlist_id, song_id)`, which is also what stops the same song being added twice (a second insert fails with `23505`). No separate unique constraint is needed. There is deliberately **no** unique constraint on `(playlist_id, position)`, so a reorder can rewrite every position in one upsert without a two-phase shuffle to dodge collisions.
- **follows** (artist follows) — `user_id (fk)`, `artist_id (fk)`
- **user_follows** — `follower_id (fk profiles, cascade)`, `following_id (fk profiles, cascade)`, `status (pending/accepted)`, `created_at` — primary key on the pair, with a check constraint blocking self-follows. One-way, Instagram-style: following a public account is accepted at once; following a private account is a pending request the owner accepts or declines. **The database sets `status`**, not the client: a before-insert trigger reads the target's `is_private`, so nobody can insert themselves straight into a private account. **Private**: only the two people in a row can select it; other people's lists come from `get_followers(target)` / `get_following(target)`, and the counts from `follow_counts(target)`. Insert as `follower_id` only; only `following_id` may update, only to `accepted`, and only the `status` column is updatable; either side may delete (unfollow, cancel, decline, remove a follower). `viewer_follows(author_id, viewer_id default auth.uid())` is the single definition of "accepted follower", used by `can_view_profile()` and reusable by the review feed. Separate from `follows`, which is artist follows.
- **friendships** — *superseded by `user_follows` in 0027 and no longer read or written by the app.* Kept, untouched along with `request_friendship()`, `friend_count()` and `get_friends()`, until the conversion has been checked; a later migration drops them. 0027 converted each accepted friendship into two accepted follows, each pending request to a private account into a pending follow, and each pending request to a public account into an accepted follow.
- **notifications** — `id`, `user_id (fk)`, `type`, `payload (jsonb)`, `read (bool)`, `created_at`. Types today: `new_follower`, `follow_requested`, `follow_accepted`, `review_liked`, `review_commented`, `thread_reply`, `artist_release`. Every row is written by a trigger calling the shared `notify(recipient_id, actor_id, type, payload)` helper, which drops the case where recipient = actor, so nobody is told about their own action. A new social type is a trigger plus one renderer. Partial unique indexes keep one `review_liked` row per (recipient, actor, review) and one `new_follower` / `follow_requested` row per (recipient, type, actor), so like -> unlike -> like and follow -> unfollow -> follow can't stack duplicates. Un-liking or deleting a comment removes the matching notification **only while it is still unread** — pulling something already seen is more confusing than leaving it. **No insert policy at all**: rows come only from database triggers (security definer) or the service role, so nobody can push a fake notification to someone else. Payloads hold ids only, never names, so the UI resolves the current name at render and a rename can't leave stale text. Pending follow requests are read live from `user_follows` for the bell and the Follow requests page; the stored `follow_requested` row is left out of the list (it would show each request twice) and is deleted when the request is accepted, declined or cancelled. Triggers on `user_follows` send `new_follower` (public account followed), `follow_requested` (private account) and `follow_accepted` (to the requester), all through `notify()`, so the per-type switches in `notification_preferences` (`new_follower`, `follow_requests`, `follow_accepted`) apply.
- **announcements** — `id`, `title`, `body`, `link` (nullable), `created_at`. Readable by any signed-in user; **writes are service-role only** and there is no admin UI — the team posts one from the Supabase SQL editor (the insert statement is documented in `supabase/migrations/0013_notifications.sql`).
- **announcement_reads** — `user_id (fk, cascade)`, `announcement_id (fk, cascade)`, `read_at` — primary key on the pair. Per-user read state, so an announcement isn't copied into every user's notifications.

## Notes

- Cache Spotify/lrclib/Genius data on first lookup rather than syncing a full catalog — the free tiers and the class-project timeline don't support a background sync job.
- `profiles.username` is unique **case-insensitively** (`profiles_username_lower_key`). The original constraint was case-sensitive, so `fara7` and `FARA7` could have coexisted.
- `playlists` and `playlist_songs` are read-public to any **signed-in** user, because playlists appear on profiles; writes are owner-only, and `playlist_songs` checks ownership through its parent playlist, so nobody can add to, reorder or empty someone else's list. Deleting a playlist cascades to its songs.
- `song_views`, `play_history`, `user_follows` and `friendships` are the tables that are **not** world-readable: browsing history is private, so even its select policy is scoped to the owner. Everything else below follows the read-public/write-own pattern.
- Every user-owned table (`profiles`, `reviews`, `review_likes`, `review_comments`, `playlists`) needs Row Level Security policies from the start: users can read public rows but only write/edit their own. Likes have no update policy — a like is binary, so it's insert or delete.
- `reviews.rating` doubles as the "5-star rating" feature and the review body — no separate ratings table needed. `title` and `body` are both nullable, so a rating-only review is valid.
- `songs.popularity` holds Deezer's `rank`, written when a row is cached. Spotify withholds its own `popularity` from this app — it's absent from search, from `/v1/tracks/{id}`, and from album tracks, and the batch endpoint is 403 — and every chart route is blocked too (editorial playlists 404/403, `/browse/*` 403, playlist track listings 403). Deezer's public API needs no key. It's matched on title + artist strings rather than an id, so it stays nullable: an unmatched track sorts last rather than being ranked zero.
- The catalog tables (`artists`, `albums`, `songs`) also carry `cached_at`, set when a row is written by the `spotify-search` Edge Function. It's what Home's Trending rail falls back to before any reviews exist.
- **The review feed (Home)** reads through `feed_for_you(min_chars, as_of, after_score, after_id, page_size)` and `feed_following(min_chars, before_at, before_id, page_size)`, both SECURITY INVOKER so the reviews RLS policy (`can_view_profile`) filters every row. Only reviews whose trimmed body has at least `min_chars` characters are listed; the app passes `FEED_MIN_CHARS` (80, `src/lib/feed.ts`), so that's the one place the threshold lives. For You excludes your own reviews and ranks by recency, likes and comments, and relevance (followed artist, liked or reviewed song, favourite genre, followed author); it pages by `(score, id)` with `as_of` fixed at the first page. Following is accepted follows plus your own reviews, newest first, paged by `(created_at, id)`. `suggested_reviewers(min_chars, max_count)` fills an empty Following tab.
