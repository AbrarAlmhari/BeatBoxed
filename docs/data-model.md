# Data Model (proposed — lock in Week 1)

This is a starting proposal for the Supabase/Postgres schema, sized to the MVP feature list. Treat it as a draft to be finalized by the team in the first work session, then locked — changes after parallel build starts should be flagged to everyone, not migrated silently.

## Core tables

- **profiles** — `id (uuid, fk auth.users)`, `username`, `display_name`, `avatar_url`, `bio`, `theme_preference`, `translation_language`, `favorite_genres`, `friends_list_visible (default true)`, `is_private (default false)`, `created_at`. `username` is unique case-insensitively, stored lowercase, and a new or changed username must be 4–20 characters of letters, numbers, `_` and `.` (trigger `profiles_username_rules`, 0037; checked only when the username is set or changed, so older shorter usernames survive other edits). `username_available(name)` checks exactly, ignoring case. `friends_list_visible` (name kept from the friends era) gates both `get_followers()` and `get_following()`, and is the Settings switch "Show my followers and following". `is_private` limits reviews, playlists, followed artists and both follow lists to accepted followers, through `can_view_profile()`; switching it from true to false accepts every pending follow request (trigger `accept_requests_on_public`).
- **artists** — `id`, `spotify_id`, `name`, `image_url`, `genres` (Spotify's; always empty with this app's credentials, unused), `genres_raw`, `genres_source (wikidata/musicbrainz/none)`, `genres_fetched_at` (Part C, see below), plus the bio and sync columns from 0025
- **albums** — `id`, `spotify_id`, `title`, `artist_id (fk)`, `cover_url`, `release_date`
- **songs** — `id`, `spotify_id`, `title`, `artist_id (fk)`, `album_id (fk)`, `duration_ms`, `genre` (kept, no longer shown anywhere in the UI: a song's genres are its artist's), `popularity` (nullable; Deezer rank, see note below)
- **reviews** — `id`, `song_id (fk)`, `user_id (fk)`, `rating (1-5)`, `title`, `body`, `created_at`, `updated_at`, `edited (bool)` — unique on `(song_id, user_id)`: one review per user per song, so writes are edit-or-create
- **review_reports** — `id`, `reporter_id (fk profiles, cascade)`, `review_id (fk reviews, cascade)`, `reason`, `created_at` — unique on `(reporter_id, review_id)`. Filled from the feed's "…" → Report. Insert only as yourself, only for a review you can see and that isn't yours; you can read only your own reports; no update or delete. No moderation screen: the team reads it in the dashboard.
- **review_likes** — `review_id (fk, cascade)`, `user_id (fk, cascade)`, `created_at` — primary key `(review_id, user_id)`, so a like is binary and can't be duplicated
- **review_comments** — `id`, `review_id (fk, cascade)`, `user_id (fk, cascade)`, `body (not null)`, `created_at`, `updated_at`, `edited (bool)`, `parent_id (fk, cascade)`, `reply_to_id (fk, set null)`, `deleted_at`. Replies are one level deep: `parent_id` is always a top-level comment on the same review (enforced by a trigger); the app sends only `reply_to_id` (the comment Reply was tapped on, which may itself be a reply) and the trigger sets `parent_id`. Deleting a top-level comment that has replies keeps it as a "Comment deleted" placeholder (`deleted_at` set, text, likes and mentions removed); without replies it's deleted outright, and the last reply leaving takes its placeholder with it. Mentions are stored in `body` as `<@user-id>` so a rename never breaks them; on save the database turns typed `@username` into that form (capitals ignored, trailing punctuation not part of the name, the longest real username for a name followed by dots), but only for people who can see the review. Readable by whoever can see the review (`can_view_review()`, 0042): signed in, `can_view_profile` on its author; logged out, public accounts only. `review_thread(review, sort)` returns a whole thread in one request; `review_previews(reviews[])` the collapsed-card data for a page of reviews.
- **comment_likes** — `comment_id (fk, cascade)`, `user_id (fk, cascade)`, `created_at`; primary key on the pair (one like per person). Insert and delete your own; readable with the review.
- **comment_mentions** — `comment_id (fk, cascade)`, `user_id (fk, cascade)`, `created_at`. Written only by the comment trigger, from the text, so it always matches it; you are never a mention in your own comment.
- **song_views** — `user_id (fk, cascade)`, `song_id (fk, cascade)`, `viewed_at` — primary key `(user_id, song_id)`, so a revisit updates the timestamp rather than adding a row. Seeds Explore's For You song rail, and feeds Explore's Recently viewed rail together with `play_history`.
- **play_history** — `user_id (fk, cascade)`, `song_id (fk, cascade)`, `played_at`, `position_seconds` — primary key `(user_id, song_id)`, so replaying a song moves its timestamp rather than adding a row. Feeds Explore's Recently viewed rail together with `song_views` (newest first, each song once). `position_seconds` is **no longer written or read**: resume-from-position was removed and every play starts from the beginning; the column stays, unused, to avoid a schema change. **Private**, scoped to the owner on every policy, like `song_views`. Kept deliberately separate from `song_views`: opening a song's page is not the same signal as listening to it. A row is only written once playback has actually run for 5 seconds, so tapping play and skipping on leaves no trace;
- **playlists** — `id`, `user_id (fk)`, `title`, `description`, `cover_url`, `created_at`, `updated_at`. `updated_at` is maintained by triggers, not the client, and moves both when the title/description change and when a song is added, removed or reordered. `cover_url` is unused: covers are derived at render time from the first four songs' album art (2×2 grid, a single image for 1–3 songs, the gradient placeholder when empty) — there is no custom cover upload.
- **playlist_songs** — `playlist_id (fk, cascade)`, `song_id (fk, cascade)`, `position`, `added_at` — primary key `(playlist_id, song_id)`, which is also what stops the same song being added twice (a second insert fails with `23505`). No separate unique constraint is needed. There is deliberately **no** unique constraint on `(playlist_id, position)`, so a reorder can rewrite every position in one upsert without a two-phase shuffle to dodge collisions.
- **playlists.is_private** (0045) — off by default. A private playlist is visible only to its owner: the select policies on `playlists` and `playlist_songs` check it, and `playlist_count()` leaves private ones out for everyone else. Otherwise a playlist is visible when its owner's account is (public, yours, or followed with an approved request). The rule lives in `playlist_visible_to(playlist, viewer)` (internal) and `can_view_playlist(playlist)` (for the caller).
- **playlist_likes** (0045) — `user_id`, `playlist_id`, `created_at`, one per person. Public: readable when you can see both the playlist and the liker's account; adding or removing only your own, and only on playlists you can see. Liking notifies the owner (`playlist_liked`, its own switch, grouped per playlist); unliking removes it while unread.
- **playlist_saves** (0045) — `user_id`, `playlist_id`, `created_at`, `last_opened_at`, one per person. Private: only the saver can read a save; the owner sees the total through `playlist_social()`. A save is a link, not a copy. `my_saved_playlists()` is the Library's Saved tab: "new songs" are songs added after `last_opened_at` (reset by `open_saved_playlist()`), and a playlist you can no longer see comes back with `available = false` and nothing else, so it can be removed. Deleting a playlist deletes its saves.
- **user_mutes** (0046) — `muter_id`, `muted_id`, `created_at`, one per pair, never yourself. Only the person who muted can read, add or remove it; there is no policy through which the muted person can read a row about them. `has_muted(muter, muted)` (internal) is the one check used by `notify()` (so no notification of any type comes from someone you muted), `comment_notification_recipients()`, `mention_suggestions()` and `review_previews()`; the feeds and the suggested-people functions read the caller's own rows. A mute doesn't touch follows in either direction.
- **song_vibes** (0048) — `song_id`, `lyrics_mood` (sad, happy, nostalgic, romantic, angry, none), `energy` (low, mid, high), `confidence` (0–1), `has_lyrics`, `model`, `labelled_at`. Written only by the `song-vibes` Edge Function (service role); signed-in users can read. Labels under 0.6 confidence are never used for picks, and a mood labelled without lyrics is capped at 0.5. **song_vibe_queue** holds songs waiting (new songs join on insert through a trigger that can never fail the insert; interacted-with songs first), **song_vibe_usage** counts calls per day for the 300-a-day cap. A pg_cron job calls the function every 10 minutes with a secret kept in Vault, checked by `song_vibes_secret_ok()`; none of these are callable through the API.
- **mood_checkins** (0048) — one per person per local day: `answers`, `shown`, `passed` ("Show another"), `status` (done, skipped). Readable only by its owner; written only through `pick_checkin_song()` and `skip_checkin()`. The pick (one function) maps the answers to a mood and an energy, ranks by taste, skips rated songs and today's, and relaxes the beat, then the mood, before returning nothing.
- **weekly_songs** (0048) — one row per Riyadh week (Monday is the key): the song, why (most rated last week, or trending as the fallback), chosen by `current_weekly_song()` on the week's first visit. `weekly_song_page()` returns the card and page data; names only of people you may see and haven't muted.
- **follows** (artist follows) — `user_id (fk)`, `artist_id (fk)`
- **user_follows** — `follower_id (fk profiles, cascade)`, `following_id (fk profiles, cascade)`, `status (pending/accepted)`, `created_at` — primary key on the pair, with a check constraint blocking self-follows. One-way, Instagram-style: following a public account is accepted at once; following a private account is a pending request the owner accepts or declines. **The database sets `status`**, not the client: a before-insert trigger reads the target's `is_private`, so nobody can insert themselves straight into a private account. **Private**: only the two people in a row can select it; other people's lists come from `get_followers(target)` / `get_following(target)`, and the counts from `follow_counts(target)`. Insert as `follower_id` only; only `following_id` may update, only to `accepted`, and only the `status` column is updatable; either side may delete (unfollow, cancel, decline, remove a follower). `viewer_follows(author_id, viewer_id default auth.uid())` is the single definition of "accepted follower", used by `can_view_profile()` and reusable by the review feed. Separate from `follows`, which is artist follows.
- **friendships** — *superseded by `user_follows` in 0027 and no longer read or written by the app.* Kept, untouched along with `request_friendship()`, `friend_count()` and `get_friends()`, until the conversion has been checked; a later migration drops them. 0027 converted each accepted friendship into two accepted follows, each pending request to a private account into a pending follow, and each pending request to a public account into an accepted follow.
- **notifications** — `id`, `user_id (fk)`, `type`, `payload (jsonb)`, `read (bool)`, `created_at`. Types today: `new_follower`, `follow_requested`, `follow_accepted`, `review_liked`, `review_commented`, `comment_reply`, `mention`, `thread_reply`, `comment_liked`, `artist_release`. Who is told about a comment or a comment like is decided in one place, `comment_notification_recipients()` (0043): each person gets at most one notification per comment, the most specific of reply > mention > comment on your review > reply in a thread you're in; `thread_reply` at most once per thread per person per hour; never the actor; never anyone who can't see the review. `group_key` (computed) marks rows shown as one line (likes on one review, likes on one comment), and `notification_unread_counts()` counts per filter with groups counted once. Who can be suggested after "@" is likewise one function, `mention_suggestions()`. Every row is written by a trigger calling the shared `notify(recipient_id, actor_id, type, payload)` helper, which drops the case where recipient = actor, so nobody is told about their own action. A new social type is a trigger plus one renderer. Partial unique indexes keep one `review_liked` row per (recipient, actor, review) and one `new_follower` / `follow_requested` row per (recipient, type, actor), so like -> unlike -> like and follow -> unfollow -> follow can't stack duplicates. Un-liking or deleting a comment removes the matching notification **only while it is still unread** — pulling something already seen is more confusing than leaving it. **No insert policy at all**: rows come only from database triggers (security definer) or the service role, so nobody can push a fake notification to someone else. Payloads hold ids only, never names, so the UI resolves the current name at render and a rename can't leave stale text. Pending follow requests are read live from `user_follows` for the bell and the Follow requests page; the stored `follow_requested` row is left out of the list (it would show each request twice) and is deleted when the request is accepted, declined or cancelled. Triggers on `user_follows` send `new_follower` (public account followed), `follow_requested` (private account) and `follow_accepted` (to the requester), all through `notify()`, so the per-type switches in `notification_preferences` (`new_follower`, `follow_requests`, `follow_accepted`) apply.
- **announcements** — `id`, `title`, `body`, `link` (nullable), `created_at`. Readable by any signed-in user; **writes are service-role only** and there is no admin UI — the team posts one from the Supabase SQL editor (the insert statement is documented in `supabase/migrations/0013_notifications.sql`).
- **announcement_reads** — `user_id (fk, cascade)`, `announcement_id (fk, cascade)`, `read_at` — primary key on the pair. Per-user read state, so an announcement isn't copied into every user's notifications.

## Notes

- Cache Spotify/lrclib/Genius data on first lookup rather than syncing a full catalog — the free tiers and the class-project timeline don't support a background sync job.
- `profiles.username` is unique **case-insensitively** (`profiles_username_lower_key`). The original constraint was case-sensitive, so `fara7` and `FARA7` could have coexisted.
- `playlists` and `playlist_songs` are read-public to any **signed-in** user, because playlists appear on profiles; writes are owner-only, and `playlist_songs` checks ownership through its parent playlist, so nobody can add to, reorder or empty someone else's list. Deleting a playlist cascades to its songs.
- `song_views`, `play_history`, `user_follows` and `friendships` are the tables that are **not** world-readable: browsing history is private, so even its select policy is scoped to the owner. Everything else below follows the read-public/write-own pattern.
- Every user-owned table (`profiles`, `reviews`, `review_likes`, `review_comments`, `playlists`) needs Row Level Security policies from the start: users can read public rows but only write/edit their own. Likes have no update policy — a like is binary, so it's insert or delete.
- `reviews.rating` doubles as the "5-star rating" feature and the review body — no separate ratings table needed. `title` and `body` are both nullable, so a rating-only review is valid.
- `songs.popularity` holds Deezer's `rank`, written when a row is cached. Spotify withholds its own `popularity` from this app — it's absent from search, from `/v1/tracks/{id}`, and from album tracks, and the batch endpoint is 403 — and every chart route is blocked too (editorial playlists 404/403, `/browse/*` 403, playlist track listings 403). Deezer's public API needs no key. It's matched on title + artist strings rather than an id, so it stays nullable: an unmatched track sorts last rather than being ranked zero.
- The catalog tables (`artists`, `albums`, `songs`) also carry `cached_at`, set when a row is written by the `spotify-search` Edge Function. It's what Home's Trending rail falls back to before any reviews exist.
- **The review feed (Home)** reads through `feed_for_you(min_chars, as_of, after_score, after_id, page_size)` and `feed_following(min_chars, before_at, before_id, page_size)`, both SECURITY INVOKER so the reviews RLS policy (`can_view_profile`) filters every row. Only reviews whose trimmed body has at least `min_chars` characters are listed; the app passes `FEED_MIN_BODY_CHARS` (20, `src/lib/feed.ts`), so that's the one place the threshold lives; star-only ratings never qualify. For You excludes your own reviews and ranks by recency, likes and comments, relevance (followed artist, liked or reviewed song, favourite genre, followed author) and length (0038: `0.5 × ln(1 + min(chars, 400) / 50)`, a gentle bonus that stops growing at 400 characters); it pages by `(score, id)` with `as_of` fixed at the first page. Following is accepted follows plus your own reviews, newest first, paged by `(created_at, id)`. `suggested_reviewers(min_chars, max_count)` fills an empty Following tab.
- **beatie_cache** — `id`, `song_id (fk songs, cascade)`, `kind (explain/line/translate)`, `line_key` (hash of the normalised line for `line`, '' otherwise), `language`, `content` (text; a JSON array of lines for `translate`), `has_lyrics`, `created_at` — unique on `(song_id, kind, line_key, language)`. Beatie's shareable answers, the same for everyone asking in the same language. Readable by any signed-in user; **no write policies**, so only the `beatie` Edge Function (service role) writes it. A row with empty `content` is an answer still being written (a claim, so it's asked of Gemini once); the function fills it in, or, if writing fails, sets `content` to `__beatie_failed__` for 2 minutes so taps meanwhile don't call Gemini again. Stale claims (3 minutes) and expired failure markers are cleared by the next request.
- **beatie_usage** — `user_id (fk profiles, cascade)`, `day`, `count` — primary key `(user_id, day)`. Beatie requests per user per UTC day; users can read only their own row and nobody can write it from the client. **beatie_global_usage** — `day`, `count` — the whole app's Gemini calls per day, with no client access at all. Both are counted only through `beatie_take_quota(user, user_limit, global_limit)`, which only the service role may call.
- **Profile stats** come from one function, `get_user_stats(user_id, range)` with range `all`, `year` (since 1 January) or `30d`. It returns jsonb: `total`, `average`, `artists` (distinct), `spread` (ratings per star, 1–5), `top_artists` (top 5: id, name, photo, count, average) and `decades` (ratings per release decade from `albums.release_date`; undated songs are left out). It's SECURITY DEFINER but checks `can_view_profile(auth.uid(), user_id)` first and returns **null** when the viewer isn't allowed, so a private account's stats reach only the owner and accepted followers. Index `reviews_user_created_idx (user_id, created_at)` serves the date ranges. The "See all" list of rated artists is read from `reviews` directly, through its RLS.
- **Artist genres (Part C).** `genre_buckets (name, short_label, priority)` lists the 16 buckets (South Asian added in 0036); `genre_map (raw → bucket)` holds exact lower-case names and `genre_patterns (pattern, bucket, priority)` LIKE patterns, both editable by the team (readable by signed-in users, no client writes). `genre_bucket_of(raw)` maps one name: exact, then the first pattern, then Other. `artist_genre_buckets(raw[])` gives an artist at most 2 buckets, the ones most of their genres fall in, ties by priority (since 0034/0035: the regional identity buckets Arabic, Khaleeji, K-Pop, South Asian first, then Pop, Hip-Hop & Rap, R&B & Soul, Rock, then the rest, Latin included), Other only when nothing else matched. `artists.genre_buckets` is a computed field over it (`select=*,genre_buckets`). The `genre_unmapped` view lists raw names that fell through to Other (service role only).
- **get_user_stats() genres** (0032): `genres` is one entry per bucket with `count` (songs), `average`, and `artists` (the 3 most rated in it). A song counts toward each of its artist's buckets, and only when rated 3★ or higher. The app shows the top 8 and folds the rest into Other, which always goes last.
- **Onboarding (0039).** `profiles` gains `setup_completed_at` (null until /welcome is finished; every account that existed when 0039 ran was marked done), `setup_step` (1–7, 8 = "All set"; resumes there), `tutorial_completed_at`, `tutorial_skipped_at` and `welcome_card_dismissed_at`. **Music tags** reuse `profiles.favorite_genres`: the user's own tags, shown on their profile; trigger `profiles_music_tags` (only when they change) trims them, drops repeats ignoring capitals, and allows at most 8 of up to 24 characters. `follows` (artist follows) gains `created_at`. Setup's suggestions come from `suggested_reviewers_for_tags(tags)`, `suggested_artists(tags)` and `suggested_songs(artist_ids, tags)`, which return only public information; `tag_buckets(tags)` turns tags into genre groups.
- **For You signals (0040):** on top of the existing score, +0.75 when the song's artist is in a genre group the viewer's tags point to, and +0.5 when the viewer liked a different song by the same artist.
- **Signup usernames (0041):** `handle_new_user()` pads names shorter than 4 and cuts names longer than 20, otherwise keeps them as typed (0037's version cut every name to 4).
